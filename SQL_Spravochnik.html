🗄 SQL: основы

SELECT, WHERE, NULL, GROUP BY, JOIN, подзапросы, оконные функции, изменение данных, ключи, индексы и транзакции — с примерами на одной учебной базе и блоками «Для QA». После изучения — флипкарты и тест.

🗄 Что такое SQL и база данных ▶

SQL (Structured Query Language) — язык запросов к реляционным базам данных. Вы не пишете, как искать данные (циклы, переборы), а описываете, что нужно получить: «дай имена пользователей из Москвы, отсортированные по возрасту». Как именно это найти, решает СУБД — это декларативный подход.

Таблица

Похожа на лист Excel: столбцы (поля) имеют имя и тип, строки (записи) — это отдельные объекты. Таблица users — пользователи, одна строка = один пользователь.

Реляционная модель

Данные разложены по нескольким таблицам, которые связаны ключами. Заказ не хранит имя клиента — только его user_id. Связь «по ключу» и есть отношение (relation).

СУБД

Программа, которая хранит данные и выполняет запросы: PostgreSQL, MySQL, MS SQL Server, Oracle, SQLite. SQL у всех почти одинаковый, но есть диалекты — различия в функциях и деталях.

Порядок строк не гарантирован

Таблица — это множество строк, а не список. Без ORDER BY база вправе вернуть строки в любом порядке, и порядок может поменяться между запусками.

Синтаксис в двух словах

  • Ключевые слова не зависят от регистра: select = SELECT. Принято писать их заглавными, чтобы отличать от имён.
  • Строки — в одинарных кавычках: 'Москва'. Двойные кавычки — для имён столбцов и таблиц: "order" (в MySQL — обратные `order`).
  • Запрос заканчивается точкой с запятой ;. Переносы строк и пробелы не важны.
  • Комментарии: -- до конца строки и /* многострочный */.

Для QA

  • SQL нужен, чтобы проверить, что действие в интерфейсе или запрос к API реально записали в базу то, что ожидалось.
  • Подготовка тестовых данных: создать пользователя с нужным статусом быстрее одним INSERT, чем через пять экранов.
  • Поиск багов в данных: дубли, «сироты» без родительской записи, пустые обязательные поля — см. раздел «SQL для QA».
  • На проде и общем стенде обычно доступ только на чтение. Любой UPDATE/DELETE — только на своём стенде и только с WHERE.
SEL SELECT: выборка и сортировка ▶

SELECT — главная команда: прочитать данные. Минимальный запрос — «какие столбцы» + «из какой таблицы». Результат запроса — тоже таблица, только временная.

1 Столбцы и псевдонимы ▶
SELECT * FROM users;                        -- все столбцы, все строки
SELECT name, city FROM users;               -- только нужные столбцы
SELECT name AS "Имя", age + 1 AS next_age   -- псевдоним (alias) и вычисление
FROM users;                                 -- Анна | 29, ..., Вера | NULL
SELECT 2 + 2;                               -- 4 (в PostgreSQL/MySQL/SQLite FROM не обязателен)

Псевдоним AS переименовывает столбец в результате (слово AS можно опустить). Таблицам тоже дают короткие псевдонимы: FROM users u — дальше пишем u.name.

✕ Частые ошибки

  1. SELECT * в автотестах и коде: добавят столбец — сломается порядок и маппинг. Перечисляйте столбцы явно.
  2. NULL + 1 даёт NULL, а не 1: у Веры next_age пустой.
2 DISTINCT — без повторов ▶
SELECT DISTINCT city FROM users;            -- Москва, СПб, Казань, NULL (4 строки)
SELECT DISTINCT user_id, status FROM orders; -- уникальны ПАРЫ значений, а не каждый столбец

DISTINCT применяется ко всей строке результата целиком. NULL считается одним значением и попадает в результат один раз.

3 ORDER BY — сортировка ▶
SELECT name, age FROM users ORDER BY age;          -- по возрастанию (ASC по умолчанию)
SELECT name, age FROM users ORDER BY age DESC;     -- по убыванию
SELECT name, city, age FROM users
ORDER BY city, age DESC;                           -- сначала по городу, внутри — по возрасту
SELECT name, age FROM users ORDER BY 2;            -- по номеру столбца (2-й = age), лучше не злоупотреблять
SELECT name, age FROM users ORDER BY age NULLS LAST; -- PostgreSQL/SQLite: куда ставить NULL

Где окажутся NULL при сортировке, зависит от СУБД: в PostgreSQL и Oracle NULL «больше всех» (в конце при ASC), в MySQL, SQLite и SQL Server — «меньше всех» (в начале).

4 LIMIT / OFFSET — первые N строк ▶
SELECT name, age FROM users ORDER BY age DESC LIMIT 2;            -- Глеб 42, Борис 35
SELECT * FROM orders ORDER BY id LIMIT 2 OFFSET 2;                -- пропустить 2, взять 2: id 3, 4
SELECT TOP 2 * FROM users;                                        -- SQL Server
SELECT * FROM users ORDER BY id FETCH FIRST 2 ROWS ONLY;          -- стандарт SQL, PostgreSQL, Oracle 12+

Для QA

  • Пагинация в API почти всегда — LIMIT/OFFSET. Проверяйте: последнюю страницу, страницу за пределами, одинаковые значения сортировки (без уникального поля в ORDER BY строки могут «прыгать» между страницами и дублироваться).
  • LIMIT без ORDER BY — «какие-то» N строк. Тест, который на это опирается, будет нестабильным.
5 Порядок выполнения запроса ▶

Пишем в одном порядке, а база выполняет в другом. Это объясняет половину ошибок: почему псевдоним из SELECT нельзя использовать в WHERE, но можно в ORDER BY.

ШагЧастьЧто происходит
1FROM / JOINСобрать исходные строки, соединить таблицы
2WHEREОтфильтровать строки
3GROUP BYРазбить на группы
4HAVINGОтфильтровать группы
5SELECTВычислить столбцы и псевдонимы, оконные функции
6DISTINCTУбрать повторы
7ORDER BYОтсортировать (псевдонимы уже известны)
8LIMIT / OFFSETОбрезать результат
 
SELECT name, age * 12 AS months FROM users WHERE months > 400;   -- ошибка: months ещё не существует
SELECT name, age * 12 AS months FROM users WHERE age * 12 > 400;  -- так правильно
SELECT name, age * 12 AS months FROM users ORDER BY months;       -- в ORDER BY псевдоним можно

SQLite и MySQL прощают псевдоним в WHERE/HAVING, PostgreSQL — нет. Пишите по стандарту, чтобы запрос работал везде.

WHR WHERE: фильтрация строк ▶

WHERE оставляет только строки, для которых условие истинно. Если условие ложно или неизвестно (NULL), строка отбрасывается.

1 Сравнение и логика ▶
SELECT name FROM users WHERE city = 'Москва';        -- Анна, Вера
SELECT name FROM users WHERE age >= 30;              -- Борис, Глеб
SELECT name FROM users WHERE city <> 'Москва';       -- Борис, Глеб  (Дина с NULL не попала!)
SELECT name FROM users WHERE city = 'Москва' AND age < 30;   -- Анна
SELECT name FROM users WHERE city = 'СПб' OR age > 40;       -- Борис, Глеб
SELECT name FROM users WHERE NOT city = 'Москва';    -- Борис, Глеб

Не равно — <> (стандарт) или != (поддерживают почти все). У AND приоритет выше, чем у OR, как у умножения перед сложением.

-- хотели: «старше 30 ИЛИ из Москвы» и при этом младше 30 — запутались в приоритете
SELECT name FROM users WHERE age > 30 OR city = 'Москва' AND age < 30;
-- читается как: age > 30 OR (city = 'Москва' AND age < 30)  → Анна, Борис, Глеб
SELECT name FROM users WHERE (age > 30 OR city = 'Москва') AND age < 30;  -- Анна

✕ Частая ошибка

  1. Смешали AND и OR без скобок. Правило: если в условии есть оба — всегда ставьте скобки.
2 IN, BETWEEN ▶
SELECT id FROM orders WHERE status IN ('new', 'cancelled');   -- 3, 4  (короче, чем два OR)
SELECT id FROM orders WHERE status NOT IN ('paid');           -- 3, 4
SELECT name FROM users WHERE age BETWEEN 19 AND 35;           -- Анна, Борис, Дина (границы ВКЛЮЧЕНЫ)
SELECT id FROM orders
WHERE created_at BETWEEN '2026-02-01' AND '2026-02-28';       -- 2, 3

✕ Ловушка с датами

  1. Если столбец хранит дату со временем, BETWEEN '2026-02-01' AND '2026-02-28' не захватит 28 февраля после 00:00. Надёжнее полуинтервал: 
    WHERE created_at >= '2026-02-01' AND created_at < '2026-03-01'
3 LIKE — поиск по шаблону ▶
SELECT name FROM users WHERE name LIKE 'А%';      -- начинается с «А»: Анна
SELECT name FROM users WHERE name LIKE '%а';      -- заканчивается на «а»: Анна, Вера, Дина
SELECT name FROM users WHERE name LIKE '_ера';    -- ровно один любой символ + «ера»: Вера
SELECT name FROM users WHERE name LIKE '%ор%';    -- содержит «ор»: Борис
SELECT email FROM users WHERE email LIKE '%\_%' ESCAPE '\';  -- ищем сам символ «_»
СимволЗначитПример
%Любое число любых символов, в том числе ноль'te%' → test, te
_Ровно один любой символ't_st' → test, tost

Чувствительность к регистру зависит от СУБД: в PostgreSQL LIKE различает регистр (для без учёта есть ILIKE), в MySQL обычно нет. Универсально: LOWER(name) LIKE 'анна%'. LIKE '%текст' с % в начале не может использовать обычный индекс — на больших таблицах это медленно.

★ — с NULL работает только IS NULL, не = NULL

∅ NULL и трёхзначная логика ▶

NULL — это не ноль и не пустая строка, а «значение неизвестно». Возраст Веры не 0 лет, он просто не указан. Отсюда главное правило: любое сравнение с неизвестным даёт неизвестность. «Вере больше 30?» — «Не знаю».

NULL

Значения нет. NULL = NULL → NULL (а не TRUE): два неизвестных не обязательно равны.

'' пустая строка

Значение есть, оно пустое. '' = '' → TRUE. (Исключение — Oracle: там '' и есть NULL.)

0

Обычное число. Баланс 0 ₽ и «баланс неизвестен» — разные состояния, и это важно для бизнес-логики.

Трёхзначная логика: TRUE, FALSE, UNKNOWN

SELECT name FROM users WHERE age = NULL;      -- пусто! сравнение с NULL всегда UNKNOWN
SELECT name FROM users WHERE age IS NULL;     -- Вера
SELECT name FROM users WHERE city IS NOT NULL;-- Анна, Борис, Вера, Глеб
SELECT NULL = NULL, NULL <> 1, NULL + 5;      -- NULL, NULL, NULL
ABA AND BA OR BNOT A
TRUENULLNULLTRUEFALSE
FALSENULLFALSENULLTRUE
NULLNULLNULLNULLNULL

Логика: FALSE AND что угодно — точно ложь; TRUE OR что угодно — точно истина. В остальных случаях с NULL ответ неизвестен.

Функции для NULL

SELECT name, COALESCE(city, 'не указан') FROM users;  -- первое не-NULL значение: Дина | не указан
SELECT COALESCE(NULL, NULL, 3, 4);                    -- 3
SELECT NULLIF(5, 5), NULLIF(5, 3);                    -- NULL, 5 (NULL, если равны)
SELECT 100 / NULLIF(0, 0);                            -- NULL вместо ошибки деления на ноль
-- IFNULL(a, b) — MySQL/SQLite, ISNULL(a, b) — SQL Server, NVL(a, b) — Oracle: всё это COALESCE на два аргумента

Для QA

  • Для каждого необязательного поля проверяйте фильтры и отчёты с NULL: «все, кроме Москвы» должны включать пользователей без города?
  • Различайте в требованиях «поле пустое» ('') и «поле не заполнено» (NULL) — API и UI часто путают их.
  • Проверка обязательных полей: SELECT COUNT(*) FROM users WHERE email IS NULL OR email = ''; — должно быть 0.
Σ Агрегаты, GROUP BY, HAVING ▶

Агрегатная функция сворачивает много строк в одно число: сколько, сумма, среднее, минимум, максимум. GROUP BY делает то же самое, но отдельно для каждой группы — как сводная таблица в Excel.

1 Агрегатные функции ▶
SELECT COUNT(*) FROM users;              -- 5   число строк
SELECT COUNT(age) FROM users;            -- 4   число НЕ-NULL значений
SELECT COUNT(DISTINCT city) FROM users;  -- 3   разных городов (NULL не считается)
SELECT SUM(amount) FROM orders;          -- 4400
SELECT AVG(age) FROM users;              -- 31.0  (124 / 4 — Вера без возраста не учтена)
SELECT MIN(amount), MAX(amount) FROM orders;  -- 200, 1500
SELECT MAX(created_at) FROM orders;      -- 2026-03-25  (MIN/MAX работают и со строками, датами)
ФункцияСчитаетNULLПустая таблица
COUNT(*)Строкисчитает0
COUNT(col)Не-NULL значенияпропускает0
SUM(col)СуммапропускаетNULL, не 0!
AVG(col)СреднеепропускаетNULL
MIN / MAXКрайние значенияпропускаетNULL

Сумма пустого набора — NULL. В отчёте «выручка за день без заказов» покажет пустоту вместо 0: оборачивайте в COALESCE(SUM(amount), 0). В PostgreSQL AVG целых чисел возвращает дробное, а в SQL Server — целое (AVG от 1 и 2 = 1): приводите к дробному типу.

2 GROUP BY — по группам ▶
SELECT status, COUNT(*) AS cnt
FROM orders
GROUP BY status;
-- cancelled | 1
-- new       | 1
-- paid      | 4

SELECT user_id, COUNT(*) AS orders_cnt, SUM(amount) AS total
FROM orders
GROUP BY user_id
ORDER BY total DESC;
-- 1 | 2 | 2000
-- 4 | 2 | 1500
-- 2 | 2 | 900

Правило: в SELECT при группировке можно писать только столбцы из GROUP BY и агрегаты. Иначе непонятно, какое значение показать: в группе paid четыре разных amount — какой из них вывести?

SELECT status, amount, COUNT(*) FROM orders GROUP BY status;
-- PostgreSQL: ERROR: column "orders.amount" must appear in the GROUP BY clause
-- MySQL (без ONLY_FULL_GROUP_BY) и SQLite: вернут СЛУЧАЙНЫЙ amount из группы — тихий баг
3 HAVING — фильтр групп ▶
-- клиенты, оплатившие больше 1000 в сумме
SELECT user_id, SUM(amount) AS paid_total
FROM orders
WHERE status = 'paid'          -- 1) сначала отбираем строки: только оплаченные
GROUP BY user_id               -- 2) группируем
HAVING SUM(amount) > 1000;     -- 3) отбираем группы
-- 1 | 2000
-- 4 | 1200

WHERE

Фильтрует строки до группировки. Агрегаты в нём нельзя: WHERE SUM(amount) > 1000 — ошибка.

HAVING

Фильтрует группы после группировки. Работает с агрегатами. Условия на обычные столбцы лучше ставить в WHERE — меньше строк попадёт в группировку.

✓ Шпаргалка ▶
SELECT   столбцы_группировки, агрегаты
FROM     таблица
WHERE    условие_на_строки
GROUP BY столбцы_группировки
HAVING   условие_на_агрегаты
ORDER BY ...
LIMIT    ...;

Для QA

  • Сверка отчёта: цифры на дашборде = SELECT COUNT(*), SUM(amount) ... GROUP BY по тем же условиям (статус, период, часовой пояс!).
  • Поиск дублей: GROUP BY email HAVING COUNT(*) > 1.
⋈ JOIN: соединение таблиц ▶

JOIN склеивает строки двух таблиц по условию в ON, обычно «внешний ключ = первичный ключ»: orders.user_id = users.id. Каждая пара строк, для которой условие истинно, даёт одну строку результата. Разные виды JOIN отличаются тем, что делать со строками, которым пары не нашлось.

ВидЧто вернётСтрок на учебной базе
INNER JOIN (или просто JOIN)Только пары, где совпало6 (Вера и Дина пропали)
LEFT JOINВсе строки левой + пары из правой, иначе NULL8 (Вера и Дина с NULL вместо заказа)
RIGHT JOINЗеркально: все строки правой6
FULL JOINВсе строки обеих, где нет пары — NULL8 (нет в MySQL)
CROSS JOINКаждая строка с каждой (декартово произведение)5 × 6 = 30

★ — 95% всех соединений

1 INNER JOIN ▶
SELECT u.name, o.id AS order_id, o.amount
FROM users u
JOIN orders o ON o.user_id = u.id
ORDER BY o.id;
-- Анна  | 1 | 500
-- Анна  | 2 | 1500
-- Борис | 3 | 700
-- Глеб  | 4 | 300
-- Глеб  | 5 | 1200
-- Борис | 6 | 200

Анна встречается дважды — у неё два заказа. JOIN «один ко многим» размножает строки левой таблицы. Пользователи без заказов исчезли.

2 LEFT JOIN и поиск «без пары» ▶
SELECT u.name, COUNT(o.id) AS orders_cnt, COALESCE(SUM(o.amount), 0) AS total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name
ORDER BY u.id;
-- Анна  | 2 | 2000
-- Борис | 2 | 900
-- Вера  | 0 | 0       ← без заказов, но в отчёте есть
-- Глеб  | 2 | 1500
-- Дина  | 0 | 0

-- анти-соединение: пользователи БЕЗ заказов
SELECT u.name
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;              -- Вера, Дина

Обратите внимание: COUNT(o.id), а не COUNT(*). У Веры одна строка с NULL вместо заказа — COUNT(*) посчитал бы её и дал 1.

✕ Ловушка: условие в WHERE превращает LEFT в INNER

  1. Хотим всех пользователей и их оплаченные заказы: 
    -- неправильно: Вера и Дина пропадут (у них o.status IS NULL, условие не выполнено)
SELECT u.name, o.amount FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.status = 'paid';
-- правильно: фильтр правой таблицы — в ON
SELECT u.name, o.amount FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'paid';
3 Несколько таблиц, self join ▶
-- цепочка: заказ → позиции → товары
SELECT o.id, p.title, oi.qty
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p     ON p.id = oi.product_id;

-- self join: таблица с самой собой (сотрудник и его руководитель)
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;

-- пары пользователей из одного города (без повторов и без пары «сам с собой»)
SELECT a.name, b.name
FROM users a JOIN users b ON a.city = b.city AND a.id < b.id;   -- Анна | Вера

Таблицы order_items, products, employees — для иллюстрации, их нет в учебной базе.

4 Размножение строк ▶

Если присоединить две «многие» таблицы к одной, строки перемножатся. У Анны 2 заказа и, скажем, 3 адреса — после двух JOIN будет 6 строк, и SUM(amount) окажется втрое больше.

-- неправильно: сумма заказов задвоится/затроится
SELECT u.name, SUM(o.amount) FROM users u
JOIN orders o    ON o.user_id = u.id
JOIN addresses a ON a.user_id = u.id
GROUP BY u.name;
-- правильно: сначала агрегировать, потом соединять
SELECT u.name, t.total
FROM users u
JOIN (SELECT user_id, SUM(amount) AS total FROM orders GROUP BY user_id) t ON t.user_id = u.id;

Для QA

  • Если в отчёте сумма или количество подозрительно кратно больше — первым делом ищите размножение строк в JOIN.
  • Сколько строк должно быть? До и после JOIN сравните COUNT(*) — это быстрая проверка, что ничего не потерялось и не размножилось.
  • Проверка целостности: заказы, у которых нет пользователя («сироты») — LEFT JOIN users ... WHERE u.id IS NULL.
5 UNION, INTERSECT, EXCEPT ▶

JOIN склеивает таблицы «вбок» (добавляет столбцы), а операции над множествами — «вниз» (складывают строки). У запросов должно быть одинаковое число столбцов совместимых типов.

SELECT city FROM users WHERE age < 30
UNION                       -- объединить и убрать дубли: NULL, Москва (2 строки)
SELECT city FROM users WHERE city = 'Москва';

SELECT user_id FROM orders WHERE status = 'paid'
UNION ALL                   -- объединить БЕЗ удаления дублей (быстрее)
SELECT user_id FROM orders WHERE status = 'new';     -- 1, 1, 4, 2, 2  (5 строк)

SELECT id FROM users
EXCEPT                      -- есть в первом, нет во втором (в Oracle — MINUS)
SELECT user_id FROM orders; -- 3, 5

SELECT id FROM users
INTERSECT                   -- есть в обоих
SELECT user_id FROM orders; -- 1, 2, 4

UNION ALL предпочтительнее, если дублей быть не может или они нужны: UNION сортирует/хеширует весь результат, чтобы убрать повторы. Для QA EXCEPT удобен для сверки двух наборов: «что есть в источнике, но не доехало в выгрузку».

( ) Подзапросы и CTE ▶

Подзапрос — запрос внутри запроса, в скобках. Результат внутреннего используется внешним: как одно число, как список значений или как временная таблица. CTE (WITH) — тот же подзапрос, но вынесенный наверх и с именем, чтобы запрос читался сверху вниз.

1 Скалярный подзапрос — одно значение ▶
-- заказы дороже среднего (среднее = 733.33)
SELECT id, amount FROM orders
WHERE amount > (SELECT AVG(amount) FROM orders);    -- 2 | 1500, 5 | 1200

-- в SELECT: доля каждого заказа от общей суммы
SELECT id, amount, ROUND(100.0 * amount / (SELECT SUM(amount) FROM orders), 1) AS pct
FROM orders;                                         -- 1 | 500 | 11.4 ...

Скалярный подзапрос обязан вернуть ровно одну строку и один столбец. Если вернёт несколько строк — ошибка (в PostgreSQL more than one row returned by a subquery), если ноль — NULL.

2 IN и NOT IN со списком ▶
SELECT name FROM users
WHERE id IN (SELECT user_id FROM orders WHERE status = 'paid');      -- Анна, Борис, Глеб

SELECT name FROM users
WHERE id NOT IN (SELECT user_id FROM orders);                        -- Вера, Дина

✕ Главная ловушка: NOT IN и NULL

  1. Если в подзапросе для NOT IN есть хотя бы один NULL, результат — пустой. 
    SELECT name FROM users WHERE id NOT IN (1, 2, NULL);    -- 0 строк!
-- id NOT IN (1, 2, NULL)  ≡  id <> 1 AND id <> 2 AND id <> NULL
-- последнее — UNKNOWN, значит всё условие никогда не TRUE
    Если в orders появится заказ гостя с user_id = NULL, запрос «пользователи без заказов» внезапно вернёт ноль строк. Используйте NOT EXISTS или LEFT JOIN ... IS NULL — они не страдают от NULL.
3 EXISTS и коррелированный подзапрос ▶
-- пользователи, у которых есть хотя бы один отменённый заказ
SELECT u.name FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.status = 'cancelled');   -- Глеб

-- пользователи без заказов — безопасно при NULL
SELECT u.name FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);   -- Вера, Дина

-- самый дорогой заказ каждого пользователя
SELECT o.user_id, o.id, o.amount FROM orders o
WHERE o.amount = (SELECT MAX(o2.amount) FROM orders o2 WHERE o2.user_id = o.user_id);
-- 1 | 2 | 1500,  2 | 3 | 700,  4 | 5 | 1200

Коррелированный подзапрос ссылается на строку внешнего (u.id) и логически выполняется для каждой его строки. EXISTS только проверяет «есть ли хоть одна строка» и останавливается на первой найденной, поэтому внутри пишут SELECT 1 — столбцы не важны.

4 Подзапрос в FROM ▶
-- средняя сумма покупок на одного покупателя
SELECT AVG(total) FROM (
  SELECT user_id, SUM(amount) AS total
  FROM orders GROUP BY user_id
) t;                                  -- (2000 + 900 + 1500) / 3 = 1466.67

Подзапросу в FROM (производной таблице) в большинстве СУБД обязательно нужен псевдоним — здесь t.

5 CTE: WITH ▶
WITH totals AS (
  SELECT user_id, SUM(amount) AS total
  FROM orders
  WHERE status = 'paid'
  GROUP BY user_id
),
vip AS (
  SELECT user_id FROM totals WHERE total >= 1200
)
SELECT u.name, t.total
FROM vip
JOIN totals t ON t.user_id = vip.user_id
JOIN users u  ON u.id = vip.user_id;     -- Анна | 2000, Глеб | 1200

CTE читается как рецепт: «сначала посчитай суммы, потом отбери VIP, потом покажи имена». Одну CTE можно использовать несколько раз, а следующая может ссылаться на предыдущую.

Рекурсивная CTE

-- числа от 1 до 5 (генератор последовательности)
WITH RECURSIVE n(x) AS (
  SELECT 1                       -- якорь: стартовая строка
  UNION ALL
  SELECT x + 1 FROM n WHERE x < 5 -- шаг: из предыдущих строк получаем новые
)
SELECT x FROM n;                 -- 1, 2, 3, 4, 5

Рекурсия нужна для деревьев: категории с подкатегориями, оргструктура, комментарии с ответами. Без условия остановки запрос будет работать бесконечно.

OVER Оконные функции ▶

Оконная функция считает что-то по группе строк, но, в отличие от GROUP BY, не сворачивает строки: каждая строка остаётся на месте и получает рядом вычисленное значение. Как если бы в Excel в каждой строке была формула «сумма по моему клиенту».

функция() OVER (
  PARTITION BY ...   -- на какие группы делить (необязательно; без него — вся таблица одно окно)
  ORDER BY ...       -- порядок внутри группы (нужен для нумерации, накопления, LAG/LEAD)
)
1 Агрегат без схлопывания ▶
SELECT id, user_id, amount,
       SUM(amount) OVER (PARTITION BY user_id) AS user_total,
       COUNT(*)    OVER ()                     AS all_cnt
FROM orders ORDER BY id;
-- 1 | 1 | 500  | 2000 | 6
-- 2 | 1 | 1500 | 2000 | 6
-- 3 | 2 | 700  | 900  | 6
-- 4 | 4 | 300  | 1500 | 6
-- 5 | 4 | 1200 | 1500 | 6
-- 6 | 2 | 200  | 900  | 6
2 Нумерация: ROW_NUMBER, RANK, DENSE_RANK ▶
SELECT name, score,
       ROW_NUMBER() OVER (ORDER BY score DESC) AS rn,
       RANK()       OVER (ORDER BY score DESC) AS rnk,
       DENSE_RANK() OVER (ORDER BY score DESC) AS drnk
FROM results;
-- A | 100 | 1 | 1 | 1
-- B |  90 | 2 | 2 | 2
-- C |  90 | 3 | 2 | 2   ← одинаковые баллы
-- D |  80 | 4 | 4 | 3   ← RANK пропускает 3, DENSE_RANK — нет

ROW_NUMBER

1, 2, 3, 4 — всегда уникальный номер. При равенстве порядок случайный.

RANK

1, 2, 2, 4 — равным одинаковое место, следующие места пропускаются (как в спорте).

DENSE_RANK

1, 2, 2, 3 — без пропусков. Удобно для «N-й по величине зарплаты».

-- топ-1 заказ каждого пользователя (классическая задача)
SELECT user_id, id, amount FROM (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY amount DESC) AS rn
  FROM orders o
) t
WHERE rn = 1;                     -- 1 | 2 | 1500,  2 | 3 | 700,  4 | 5 | 1200

Оконную функцию нельзя писать в WHERE (она вычисляется на шаге SELECT), поэтому фильтр — во внешнем запросе или CTE.

3 Накопительный итог, LAG / LEAD ▶
SELECT created_at, amount,
       SUM(amount) OVER (ORDER BY created_at)       AS running_total,
       LAG(amount)  OVER (ORDER BY created_at)      AS prev_amount,
       amount - LAG(amount) OVER (ORDER BY created_at) AS diff
FROM orders;
-- 2026-01-10 | 500  | 500  | NULL | NULL
-- 2026-02-03 | 1500 | 2000 | 500  | 1000
-- 2026-02-15 | 700  | 2700 | 1500 | -800
-- 2026-03-01 | 300  | 3000 | 700  | -400
-- 2026-03-20 | 1200 | 4200 | 300  | 900
-- 2026-03-25 | 200  | 4400 | 1200 | -1000

LAG — значение из предыдущей строки, LEAD — из следующей. Для первой строки предыдущей нет — NULL (можно задать значение по умолчанию: LAG(amount, 1, 0)). Когда в окне есть ORDER BY, SUM по умолчанию считает «от начала до текущей строки» — отсюда накопительный итог.

DML INSERT, UPDATE, DELETE ▶

Команды, которые меняют строки. Главное правило безопасности: UPDATE и DELETE без WHERE затрагивают всю таблицу. Перед изменением выполните тот же запрос как SELECT и посмотрите, какие строки попадут.

1 INSERT — добавить ▶
INSERT INTO users (name, city, age) VALUES ('Егор', 'Тула', 31);   -- id подставится сам
INSERT INTO users (name, city) VALUES                              -- несколько строк сразу
  ('Жанна', 'Омск'),
  ('Зоя', NULL);                                                   -- age не указан → NULL (или DEFAULT)
INSERT INTO archive_orders (id, amount)                            -- вставить результат запроса
SELECT id, amount FROM orders WHERE created_at < '2026-02-01';
INSERT INTO users (name) VALUES ('Ия') RETURNING id;               -- PostgreSQL/SQLite: сразу получить новый id

Всегда перечисляйте столбцы: INSERT INTO users VALUES (...) без списка сломается, когда в таблицу добавят столбец.

2 UPDATE — изменить ▶
UPDATE orders SET status = 'paid' WHERE id = 3;                  -- одна строка
UPDATE users SET city = 'Москва', age = age + 1 WHERE id = 5;    -- несколько столбцов
UPDATE orders SET amount = amount * 0.9 WHERE status = 'new';    -- скидка 10% всем новым
UPDATE orders SET status = 'cancelled';                          -- !!! ВСЕ заказы отменены
-- безопасный приём: сначала SELECT с тем же WHERE
SELECT * FROM orders WHERE status = 'new' AND created_at < '2026-03-01';   -- 1 строка, ок
BEGIN;
UPDATE orders SET status = 'cancelled' WHERE status = 'new' AND created_at < '2026-03-01';
-- проверили результат → COMMIT;  что-то не так → ROLLBACK;
3 DELETE, TRUNCATE, DROP ▶
DELETE FROM orders WHERE status = 'cancelled';   -- удалить подходящие строки
DELETE FROM orders;                              -- удалить все строки (таблица остаётся)
TRUNCATE TABLE orders;                           -- быстро очистить таблицу целиком
DROP TABLE orders;                               -- удалить саму таблицу вместе со структурой

Мягкое удаление (soft delete): вместо DELETE ставят флаг deleted_at = now(), а все запросы фильтруют WHERE deleted_at IS NULL. Данные можно восстановить, история сохраняется.

4 UPSERT — вставить или обновить ▶
-- PostgreSQL / SQLite: если такой email уже есть — обновить имя
INSERT INTO users (email, name) VALUES ('a@x.ru', 'Анна')
ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name;

-- MySQL
INSERT INTO users (email, name) VALUES ('a@x.ru', 'Анна')
ON DUPLICATE KEY UPDATE name = VALUES(name);

-- стандарт SQL, SQL Server, Oracle, PostgreSQL 15+: MERGE

Для QA

  • Тестовые данные удобно готовить скриптом INSERT и убирать за собой DELETE ... WHERE name LIKE 'autotest_%' — помечайте свои записи префиксом.
  • Ещё надёжнее — тест внутри транзакции с ROLLBACK в конце: база вернётся в исходное состояние.
  • Проверяйте поведение повторной отправки формы/запроса: создаётся дубль или срабатывает уникальность/UPSERT (идемпотентность).
DDL Таблицы, типы, ключи и ограничения ▶

DDL описывает структуру: какие таблицы, какие у них столбцы и типы, какие правила обязаны соблюдать данные. Ограничения (constraints) — это защита на уровне базы: даже если приложение с багом попробует записать мусор, база откажет.

1 CREATE TABLE ▶
CREATE TABLE users (
  id         SERIAL PRIMARY KEY,                 -- автоинкремент (PostgreSQL); MySQL: INT AUTO_INCREMENT
  email      VARCHAR(255) NOT NULL UNIQUE,       -- обязательный и уникальный
  name       VARCHAR(100) NOT NULL,
  age        INT CHECK (age BETWEEN 0 AND 150),  -- проверка значения
  balance    NUMERIC(12, 2) NOT NULL DEFAULT 0,  -- деньги: точный тип, по умолчанию 0
  is_active  BOOLEAN NOT NULL DEFAULT TRUE,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE orders (
  id      SERIAL PRIMARY KEY,
  user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,   -- внешний ключ
  amount  NUMERIC(12, 2) NOT NULL CHECK (amount > 0),
  status  VARCHAR(20) NOT NULL DEFAULT 'new'
);

Первичный ключ

«Паспорт» строки: users.id. Обычно суррогатный — число или UUID без смысла, а не email или телефон (они меняются).

Внешний ключ

Ссылка на паспорт в другой таблице: orders.user_id → users.id. Не даёт создать заказ несуществующему пользователю.

4 ALTER и DROP ▶
ALTER TABLE users ADD COLUMN phone VARCHAR(20);            -- добавить столбец (у старых строк — NULL)
ALTER TABLE users DROP COLUMN phone;                       -- удалить столбец
ALTER TABLE users RENAME COLUMN name TO full_name;         -- переименовать
ALTER TABLE users ALTER COLUMN age SET NOT NULL;           -- PostgreSQL; упадёт, если уже есть NULL
ALTER TABLE orders ADD CONSTRAINT chk_amount CHECK (amount > 0);
DROP TABLE IF EXISTS tmp_import;                           -- без ошибки, если таблицы нет

Для QA

  • Проверка ограничений — граничные значения: пустая строка, NULL, строка длиной n и n+1 для VARCHAR(n), 0 и отрицательные для CHECK (amount > 0), дубль для UNIQUE.
  • Ошибка базы не должна долетать до пользователя как «500 + текст SQL». Ожидается понятное сообщение и корректный код ответа (409 на дубль, 400/422 на невалидные данные).
  • Миграции: после ALTER старые данные должны остаться корректными — проверяйте новый столбец у существующих строк.
5 Нормализация и связи ▶

Нормализация — раскладка данных так, чтобы каждый факт хранился в одном месте. Если имя клиента записано в каждом его заказе, при смене имени придётся править десятки строк, и где-нибудь забудут — данные разойдутся (аномалия обновления).

1НФ

В ячейке одно значение: не phones = '111, 222', а отдельная таблица телефонов.

2НФ

1НФ + каждый неключевой столбец зависит от всего составного ключа, а не от его части.

3НФ

2НФ + неключевые столбцы не зависят друг от друга: город клиента — в users, а не в orders.

СвязьПримерКак устроена
Один к одномуПользователь — профильFK + UNIQUE во второй таблице
Один ко многимПользователь — заказыFK в таблице «многих»: orders.user_id
Многие ко многимЗаказы — товарыСвязующая таблица order_items(order_id, product_id)

Денормализация — сознательное дублирование ради скорости чтения (например, хранить orders_count у пользователя). Тогда появляется риск рассинхрона, и это хорошее место для проверок QA.

⚡ Индексы и транзакции ▶
1 Индекс — оглавление таблицы ▶

Без индекса поиск WHERE email = 'a@x.ru' — это чтение всей таблицы подряд (full scan), как поиск слова в книге без предметного указателя. Индекс — отсортированная структура (обычно B-дерево), по которой нужная строка находится за несколько шагов даже среди миллионов.

CREATE INDEX idx_orders_user ON orders(user_id);                -- обычный
CREATE UNIQUE INDEX idx_users_email ON users(email);            -- ещё и запрещает дубли
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at); -- составной
DROP INDEX idx_orders_user;

Плюсы

Быстрые WHERE, JOIN, ORDER BY по индексированным столбцам. PRIMARY KEY и UNIQUE создают индекс автоматически.

Минусы

Занимают место и замедляют INSERT/UPDATE/DELETE: при каждом изменении индекс тоже нужно обновить. Индексировать всё подряд — плохо.

Когда индекс НЕ используется

  • Функция над столбцом: WHERE LOWER(email) = ..., WHERE YEAR(created_at) = 2026 (нужен функциональный индекс или условие-диапазон).
  • LIKE '%abc' — шаблон начинается с %.
  • Составной индекс (user_id, created_at), а фильтр только по created_at — работает правило «левого префикса».
  • Неявное приведение типов: столбец строковый, а сравниваем с числом.
  • Маленькая таблица или условие подходит большинству строк — полный просмотр дешевле.
EXPLAIN SELECT * FROM orders WHERE user_id = 1;           -- план: Index Scan или Seq Scan?
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 1;   -- PostgreSQL: выполнить и показать реальное время
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE user_id = 1; -- SQLite
2 Транзакции и ACID ▶

Транзакция — группа операций, которая выполняется целиком или не выполняется вовсе. Классика — перевод денег: списать с одного счёта и зачислить на другой. Если после списания сервер упал, без транзакции деньги просто исчезнут.

BEGIN;                                                    -- START TRANSACTION в MySQL
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;                                                   -- зафиксировать оба изменения
-- при ошибке: ROLLBACK;                                  -- отменить всё с момента BEGIN

BEGIN;
INSERT INTO orders ...;
SAVEPOINT sp1;                                            -- точка сохранения
UPDATE ...;
ROLLBACK TO sp1;                                          -- откатить только UPDATE
COMMIT;
БукваСвойствоПростыми словами
AAtomicity — атомарностьВсё или ничего
CConsistency — согласованностьПосле транзакции все ограничения соблюдены (нет отрицательных балансов, висячих FK)
IIsolation — изолированностьПараллельные транзакции не мешают друг другу (насколько — задаёт уровень изоляции)
DDurability — долговечностьПосле COMMIT данные не пропадут даже при отключении питания

Режим автофиксации (autocommit): в большинстве клиентов каждая команда без явного BEGIN сразу фиксируется — откатить её уже нельзя. А вот в некоторых клиентах (Oracle SQL Developer, DBeaver в ручном режиме) наоборот: пока не сделали COMMIT, другие ваших изменений не видят.

Грязное чтение

Видим чужие незафиксированные изменения, а потом их откатили — мы работали с данными, которых «не было».

Неповторяющееся чтение

Прочитали строку дважды в одной транзакции, а между чтениями её изменили и зафиксировали — значения разные.

Фантомы

Повторный SELECT ... WHERE вернул новые строки, которые кто-то вставил между запросами.

Потерянное обновление

Два процесса прочитали баланс 100, каждый прибавил 50 и записал 150 — одно пополнение потеряно. Лечится UPDATE ... SET b = b + 50, SELECT ... FOR UPDATE или версией строки.

Взаимоблокировка (deadlock): транзакция A держит строку 1 и ждёт строку 2, транзакция B — наоборот. СУБД обнаруживает цикл и откатывает одну из них с ошибкой.

Для QA

  • Гонки проверяют параллельными запросами: двойной клик «Оплатить», два одновременных списания с одного баланса, покупка последнего товара двумя пользователями.
  • Если при ошибке на середине операции часть данных записалась (заказ есть, а оплаты нет) — это баг атомарности.
  • Медленный экран → попросите EXPLAIN запроса или проверьте, есть ли индекс по столбцу фильтра.
f() Функции: CASE, строки, даты, типы ▶

Набор встроенных функций сильнее всего отличается между СУБД. Ниже — самое ходовое; если не сработало, ищите аналог для своей базы.

1 CASE — if/else в запросе ▶
SELECT name, age,
  CASE
    WHEN age IS NULL THEN 'неизвестно'
    WHEN age < 30    THEN 'до 30'
    ELSE '30+'
  END AS age_group
FROM users;
-- Анна 28 до 30, Борис 35 30+, Вера NULL неизвестно, Глеб 42 30+, Дина 19 до 30

-- условная агрегация: несколько счётчиков за один проход
SELECT
  COUNT(*)                                          AS all_orders,  -- 6
  SUM(CASE WHEN status = 'paid' THEN 1 ELSE 0 END)  AS paid,        -- 4
  SUM(CASE WHEN status = 'paid' THEN amount END)    AS paid_sum     -- 3400
FROM orders;

Ветки проверяются сверху вниз, срабатывает первая истинная. Без ELSE несовпавшие получат NULL. В PostgreSQL условную агрегацию можно записать короче: COUNT(*) FILTER (WHERE status = 'paid').

2 Строки ▶
SELECT 'Анна' || ' ' || 'Ли';           -- Анна Ли   (стандарт; MySQL: CONCAT('Анна', ' ', 'Ли'))
SELECT UPPER('qa'), LOWER('QA');        -- QA, qa
SELECT LENGTH('тест');                  -- 4 (MySQL LENGTH считает байты → 8; символы — CHAR_LENGTH)
SELECT TRIM('  hi  ');                  -- 'hi'
SELECT SUBSTR('2026-03-20', 1, 7);      -- 2026-03  (SUBSTRING в PostgreSQL/MySQL/SQL Server)
SELECT REPLACE('a-b-c', '-', '/');      -- a/b/c
SELECT INSTR('qa@mail.ru', '@');        -- 3  (POSITION('@' IN ...) в PostgreSQL)
3 Даты ▶
SELECT CURRENT_DATE, CURRENT_TIMESTAMP;              -- везде
SELECT NOW();                                        -- PostgreSQL, MySQL
SELECT created_at + INTERVAL '7 days' FROM orders;   -- PostgreSQL (MySQL: + INTERVAL 7 DAY)
SELECT date(created_at, '+7 days') FROM orders;      -- SQLite
SELECT EXTRACT(YEAR FROM created_at) FROM orders;    -- PostgreSQL/MySQL: 2026
SELECT DATE_TRUNC('month', created_at) FROM orders;  -- PostgreSQL: начало месяца
SELECT strftime('%Y-%m', created_at) AS month, SUM(amount)   -- SQLite: выручка по месяцам
FROM orders GROUP BY month;                          -- 2026-01 | 500, 2026-02 | 2200, 2026-03 | 1700

✕ Даты и часовые пояса

  1. В базе время обычно в UTC, в интерфейсе — местное. Заказ в 01:00 по Москве 1 марта лежит в базе как 22:00 28 февраля и попадёт в февральский отчёт.
  2. Не сравнивайте даты как строки в разных форматах: '20.03.2026' > '1.04.2026' — строковое сравнение посимвольное. Формат YYYY-MM-DD сортируется правильно.
4 Числа и приведение типов ▶
SELECT 7 / 2;                     -- 3  (целочисленное деление в PostgreSQL, SQLite, SQL Server; в MySQL — 3.5)
SELECT 7 / 2.0;                   -- 3.5
SELECT CAST(7 AS REAL) / 2;       -- 3.5  (стандарт CAST)
SELECT 7::numeric / 2;            -- PostgreSQL-сокращение
SELECT ROUND(733.3333, 2);        -- 733.33
SELECT 7 % 3;                     -- 1   остаток (MOD(7, 3) в Oracle)
SELECT ABS(-5);                   -- 5
SELECT CAST('42' AS INTEGER) + 1; -- 43

Целочисленное деление — частый баг процентов: paid_cnt / all_cnt * 100 даст 0 вместо 66, потому что 4 / 6 = 0. Умножайте сначала на 100.0.

QA SQL для тестировщика ▶

Готовые запросы, которые закрывают типичные проверки данных. Подставьте свои таблицы и столбцы. Хорошая проверка — запрос, который при отсутствии бага возвращает 0 строк: его легко превратить в автотест.

1 Проверка после действия ▶
-- зарегистрировали пользователя через UI/API — что реально легло в базу?
SELECT id, email, status, created_at
FROM users
WHERE email = 'autotest_42@example.com';

-- последние записи: что создалось за последние минуты
SELECT * FROM orders ORDER BY id DESC LIMIT 10;

-- связанные данные создались все (заказ → позиции → платёж)
SELECT o.id, COUNT(oi.id) AS items, p.status AS payment
FROM orders o
LEFT JOIN order_items oi ON oi.order_id = o.id
LEFT JOIN payments p     ON p.order_id = o.id
WHERE o.id = 1001
GROUP BY o.id, p.status;
2 Целостность данных ▶
-- дубли по полю, которое должно быть уникальным
SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1;

-- «сироты»: заказы несуществующих пользователей (если FK не настроен)
SELECT o.* FROM orders o LEFT JOIN users u ON u.id = o.user_id WHERE u.id IS NULL;

-- пустые обязательные поля
SELECT id FROM users WHERE email IS NULL OR TRIM(email) = '';

-- недопустимые значения статусов
SELECT DISTINCT status FROM orders WHERE status NOT IN ('new', 'paid', 'cancelled');

-- нарушение бизнес-правил: оплачен, но без даты оплаты; дата окончания раньше начала
SELECT id FROM orders WHERE status = 'paid' AND paid_at IS NULL;
SELECT id FROM promo WHERE ends_at < starts_at;

-- денормализованный счётчик разошёлся с реальным количеством
SELECT u.id, u.orders_count, COUNT(o.id) AS real_count
FROM users u LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.orders_count
HAVING u.orders_count <> COUNT(o.id);
3 Сверка двух источников ▶
-- количество и сумма совпадают? (до/после миграции, источник/выгрузка)
SELECT COUNT(*), SUM(amount) FROM orders;
SELECT COUNT(*), SUM(amount) FROM orders_export;

-- какие строки есть в источнике, но не доехали
SELECT id, amount FROM orders
EXCEPT
SELECT id, amount FROM orders_export;
4 SQL-инъекции ▶

SQL-инъекция возникает, когда приложение склеивает запрос из строки пользователя. Ввод становится частью кода запроса и меняет его смысл.

-- приложение делает: "SELECT * FROM users WHERE login = '" + login + "' AND pass = '" + pass + "'"
-- пользователь вводит в логин:   admin' --
SELECT * FROM users WHERE login = 'admin' --' AND pass = '...'
-- всё после -- стало комментарием: вход без пароля

-- ввод:   ' OR '1'='1
SELECT * FROM users WHERE login = '' OR '1'='1' AND pass = '' OR '1'='1'
-- условие истинно для всех строк

Как защищаются

Параметризованные запросы (prepared statements): WHERE login = ?, значение передаётся отдельно и никогда не становится кодом. ORM делает это сам.

Как проверяет QA

В поля ввода, параметры URL и JSON — ', ", ' OR '1'='1, '; --. Тревожные признаки: ошибка 500 с текстом SQL, изменение выдачи, задержка от pg_sleep(5)/SLEEP(5).

Для QA

  • Апостроф в обычных данных (O'Brien, «Д'Артаньян») — законный тест: имя должно сохраниться без ошибки и без искажений.
  • Проверяйте инъекции только на своих стендах и в рамках согласованного тестирования безопасности.

★ — любимые вопросы на собеседованиях

Вопросы с собеседований

  1. Чем WHERE отличается от HAVING? WHERE фильтрует строки до группировки и не может содержать агрегаты; HAVING фильтрует группы после GROUP BY.
  2. Виды JOIN и разница INNER / LEFT? INNER — только совпавшие пары; LEFT — все строки левой таблицы, для несовпавших справа NULL. Есть ещё RIGHT, FULL, CROSS, self join.
  3. DELETE vs TRUNCATE vs DROP? DELETE — строки по условию, построчно, с триггерами; TRUNCATE — быстро все строки; DROP — удаляет таблицу целиком.
  4. Первичный ключ vs уникальный? PK — один на таблицу, не допускает NULL, идентифицирует строку. UNIQUE — сколько угодно, обычно допускает NULL.
  5. Что такое внешний ключ? Столбец, значение которого должно существовать в первичном ключе другой таблицы; обеспечивает ссылочную целостность.
  6. Что такое индекс, плюсы и минусы? Структура для быстрого поиска; ускоряет чтение, замедляет запись и занимает место.
  7. Расшифруйте ACID. Atomicity, Consistency, Isolation, Durability.
  8. UNION vs UNION ALL? UNION убирает дубли (дороже), UNION ALL — нет.
  9. Как найти дубли? GROUP BY поле HAVING COUNT(*) > 1.
  10. Вторая по величине зарплата? SELECT MAX(salary) FROM emp WHERE salary < (SELECT MAX(salary) FROM emp) или DENSE_RANK() = 2.
  11. Как найти пользователей без заказов? LEFT JOIN ... WHERE o.id IS NULL или NOT EXISTS; осторожно с NOT IN и NULL.
  12. Порядок выполнения SELECT? FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT.
  13. Что такое нормализация? Раскладка данных по таблицам без дублирования фактов; 1НФ — атомарные значения, 2НФ — зависимость от всего ключа, 3НФ — нет зависимостей между неключевыми полями.
  14. Чем оконная функция отличается от GROUP BY? Оконная не схлопывает строки: каждая строка остаётся и получает вычисленное по окну значение.
  15. Что такое транзакция и уровни изоляции? Группа операций «всё или ничего»; уровни — READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE — от слабой к полной изоляции.
  16. Как проверить, что данные из UI сохранились верно? Найти запись по уникальному признаку, сверить каждое поле, связанные таблицы, типы, часовой пояс и отсутствие дублей.
